## Problem

The kit's agent vocabulary is incomplete. `runtime/agents/` today
ships only `executor.md` and `verifier.md` — both downstream
roles. There is no kit-shipped role for **producing upstream
documents** (PRDs, and eventually specs / reviews / changelog).

When v0.5.0 added Step 0 (define PRD) to
`runtime/workflows/feature-development.md`, the pipeline started
demanding an upstream producer, but the agent roster did not
gain one. The project-side `write-a-prd` skill at
`.ai/project/skills/product/write-a-prd/SKILL.md` documents the
**task pattern** (11-step elicit-then-write procedure), but not
the **role**. As a result, an AI agent reading
`runtime/BOOTSTRAP.md` and being asked to draft a PRD has no
canonical role to step into — the agent improvises from the
template alone, with no role-level inputs / outputs / constraints
to anchor behavior across invocations or across consumers.

Evidence is structural rather than reported: `runtime/INDEX.md` §
Agents lists two role files plus three transition-only concepts
(architect / planner / reviewer) explicitly marked "no
dedicated role file." That gap is fine when the workflow doesn't
demand the role; v0.5.0 closed that loophole for the PRD step.

## Target Users

- **PM / founder / product owner using ai-runtime-kit.** Asks
  their AI agent "write a PRD for X" during Step 0 of a
  product-driven feature. Without `prd-writer.md`, identical
  requests across sessions can produce structurally different
  PRDs because no kit-shipped role anchors agent behavior.
- **AI agent reading the kit's BOOTSTRAP and workflows.** When
  `feature-development.md` Step 0 instructs "draft a PRD," the
  agent needs a role file to step into — the same way
  `executor.md` anchors implementation work. Without
  `prd-writer.md`, the agent has no role-level contract to
  honor, only a template and an optional project-side skill.

## Success Metrics

- **M1 — Structural completeness ≥90%.** PRDs generated by an
  agent that read `runtime/agents/prd-writer.md` have all 7
  template sections (Problem / Target Users / Success Metrics /
  User Stories / Out of Scope / Open Questions / Stakeholders)
  non-empty. Spot-check ≥5 PRDs to compute the rate.
- **M2 — Turn budget ≤10.** From "write me a PRD for X" to PRD
  file saved at `.ai/project/prds/YYYY-MM-DD-<slug>/prd.md`, the
  elicitation conversation completes in ≤10 turns. Measured by
  counting user-assistant turn pairs.
- **M4 — External adoption signal.** Within 60 days of the
  release that ships `prd-writer.md`, **≥1 external kit consumer**
  (currently the only one is ai-workflow-demo) produces a PRD file
  under their `.ai/project/prds/`. Weak signal — only one external
  consumer exists — but the only objective "feature got used"
  check available at v0.x scale.

## User Stories

- **As a PM** using ai-runtime-kit, **I want** to ask my AI agent
  "write a PRD for X" and have it enter a standardized
  `prd-writer` role, **so that** the resulting PRD has predictable
  shape (7 template sections, DRAFT status, elicit-not-assume
  discipline) without me coaching the agent each time.
- **As an AI agent** following `feature-development.md` Step 0,
  **I want** `runtime/agents/prd-writer.md` to define my role with
  explicit inputs / outputs / constraints, **so that** my PRD
  output is consistent across invocations and across consumers.

## Out of Scope

- **Other writer-family agents** (`spec-writer`, `review-writer`,
  `changelog-writer`). v1 is PRD-only; parallel agents open only
  when the analogous need surfaces (e.g. an internal spec author
  who wants the same kind of role anchor).
- **Cross-agent tool integration** (Claude Code `/prd-writer`
  slash command, Cursor mode, Aider command, etc.). The agent is
  a markdown role definition; tool-specific surfaces are
  downstream concerns and likely belong to consumer projects, not
  the kit.
- **PRD lifecycle enforcement** (making PRDs mandatory upstream
  of all specs, gating spec creation on APPROVED PRD status,
  auto-promoting DRAFT → APPROVED). v0.5.0 deliberately kept
  PRDs optional; this PRD does not change that.
- **PRD template content changes** (adding / removing sections,
  "lite" vs "full" variants). The template at
  `runtime/prds/_template.md` was finalized in v0.5.0 and stays
  unchanged here.

## Open Questions

PRD-elicit-phase questions are all resolved. The single
structural decision is recorded below for traceability; remaining
items are spec-phase, not PRD-blocking.

**Resolved during elicit:**

- **Q1 — Relationship between `prd-writer` agent and the existing
  `.ai/project/skills/product/write-a-prd/SKILL.md` skill.**
  **Decision: R2 — coexist.**
  - `runtime/agents/prd-writer.md` is the **role** (short
    executor-style definition; the agent's identity,
    inputs/outputs, constraints).
  - `.ai/project/skills/product/write-a-prd/SKILL.md` is the
    **task pattern** (the 11-step procedure for elicit-then-write).
  - The agent file references the skill by path so an agent
    reading `prd-writer.md` knows where to find the procedural
    depth.
  - Skill stays project-side (this repo's dogfood);
    agent ships in `runtime/`. Concept lattice: **agent = WHO,
    skill = HOW.**
  - Decided by: kaelen (during PRD elicit, 2026-05-14).

**Deferred to downstream spec (not PRD-blocking):**

- Agent file depth — short like `executor.md` (~300 chars) or
  richer body? Spec decides based on R2's "agent = role" framing.
- `runtime/INDEX.md` placement — append a bullet to the existing
  `## Agents` section, or open a subsection? Spec decides.
- Whether to update `runtime/INDEX.md`'s "transition-only
  concepts" note (architect / planner / reviewer) now that one
  of the previously transition-only roles has gained a file.
